SCOPE (read this first, it is binding)
--------------------------------------------------------------------------------
This is a STRUCTURAL refactor ONLY. Ports-and-adapters (hexagonal) + dependency
injection at the composition root. Rust-idiomatic.

  * NO new features. NO new tools. NO new backends (no SQLite-graph, no Postgres,
    no S3, no dynamic language packs, no pipeline-stage plugins). Those are FUTURE
    work that this refactor merely UNBLOCKS.
  * NO behaviour change. Every MCP tool, every search mode, every CLI flag must
    behave identically before and after. Same on-disk index layout
    (meta.db / tantivy/ / graph.bin / vectors.json). Indices remain rebuildable.
  * The DELIVERABLE is seams: trait-based ports for every major concern, the
    existing concrete types demoted to adapters implementing those ports, and a
    single composition root that injects them.

INVARIANTS (from steering — do not violate)
--------------------------------------------------------------------------------
  * 100% safe Rust. unsafe_code = forbid. MSRV 1.80, edition 2021.
  * No backwards-compat shims, no aliased/duplicate paths, no dead code. When a
    type/accessor is replaced, DELETE the old shape in the SAME task.
  * missing_docs = warn: every new public trait/type/method gets a doc comment.
  * Clippy runs with -D warnings; do NOT silence with blanket #[allow]. Fix roots.
  * Layering stays: common (no deps) <- core <- mcp <- cli. Ports live low; no
    upward or circular deps. Adapters never leak their concrete backend types
    (rusqlite::Connection, tantivy::*, hnsw_rs::*, petgraph::*) across a port.

TARGET ARCHITECTURE (reference — the shape all phases build toward)
--------------------------------------------------------------------------------
Ports (traits) — the contracts. Candidate home: ctxvault-common (or a new
ctxvault-ports module if common would gain heavy deps; prefer keeping port
TRAITS dep-light and letting ADAPTERS in core pull the heavy crates):

  MetadataCatalog   — file records, chunks, code_symbols, edge_types,
                      templates, indexing_state, corpus_config (today: Store)
  TextIndex         — add/remove/commit/search_with_modality       (today: BM25Index)
  VectorStore       — add/add_batch/remove/search/save/load/dirty  (today: VectorIndex)
  GraphStore        — nodes/edges/traverse/backlinks/communities/save/load
                                                                    (today: KnowledgeGraph)
  EmbeddingProvider — embed_query/embed_batch/dimensions/model_ver (today: Embedder)
  SearchService     — search(mode, query, opts) -> results; owns the mode dispatch
                      currently living in the mcp handle_search match.

Adapters (implement the ports; keep concrete backend crates encapsulated):
  SqliteCatalog(Store) · TantivyTextIndex(BM25Index) · HnswVectorStore(VectorIndex)
  PetgraphStore(KnowledgeGraph) · OnnxEmbedder(Embedder)

Composition root: ctxvault-cli/main.rs builds concrete adapters and injects them
via an EngineBuilder; CorpusManager routes over port-typed engines. mcp depends
on port traits + SearchService, never on concrete core internals.

Rust DI policy:
  * Generics + trait bounds for the stable hot path (monomorphized, zero-cost).
  * Trait objects (Arc<dyn ...>/Box<dyn ...>) only where runtime swap is the point.
  * Constructor injection assembled once at the composition root (main.rs).
  Decide generic-vs-dyn per port in Phase 1 and record it (Task 1.5).

PHASE 3 — MAKE Engine DEPEND ON PORTS + COMPOSITION ROOT
================================================================================
Goal: Engine holds ports, not concrete backends; a builder injects the concrete
adapters; the leaky accessors are deleted.

*** PHASE 3 WIRING DECISION (BINDING — user-approved, supersedes "generic over 5
    params" where they conflict) : APPROACH B — CONCRETE Engine + PORT-TYPED
    ACCESSORS + BUILDER INJECTION. ***
  Rationale: the mcp tool layer stores handlers as fn-pointers
  (`fn(&Engine, Value)`), and CorpusManager holds `HashMap<String, Engine>`.
  A fully generic `Engine<C,T,V,G,E>` would EITHER force concrete backend type
  NAMES back into the mcp crate (violating Task 4.2's "zero concrete backend types
  in mcp" grep) OR thread 5 type params through ToolRegistry/MultiCorpusToolRegistry/
  CorpusManager/transport-state/cli (viral churn). Neither is warranted: there is
  NO runtime/compile-time backend-swap seam in scope today (the ports.rs decision
  block itself says none needs dyn).
  THEREFORE for this refactor:
   - Engine STAYS ONE CONCRETE TYPE holding the 5 concrete adapters as fields
     (Store, BM25Index, VectorIndex, KnowledgeGraph, Embedder). Do NOT parameterize
     Engine, CorpusManager, the tool registry, transport, or cli over the ports.
   - Engine is the CONCRETE COMPOSITION EPICENTER. It exposes its backends to
     consumers ONLY through PORT-TYPED accessors/methods (`&impl GraphStore`,
     `&impl MetadataCatalog`, etc. — or narrow domain methods), never returning the
     concrete backend type. Consumers (mcp, CorpusManager) depend on the ports.
   - The COMPOSITION ROOT (cli/main.rs) is the ONLY place the 5 concrete adapters
     are NAMED + CONSTRUCTED; it injects them into Engine via the builder.
   - FUTURE VARIANTS (e.g. a Lambda/S3/Postgres target) arrive as a NEW crate with
     its own concrete adapters implementing the same ports + its own composition
     root that assembles a differently-wired Engine. The Phase-1 ports are exactly
     what makes that additive. Whether to genericize Engine THEN, or give each
     variant crate its own assembler, is a FUTURE decision the ports unblock — do
     NOT prejudge or build it now (OUT OF SCOPE).
   - The ports.rs "hot-path = generics" note describes the FUTURE swap mechanism;
     it does not require parameterizing Engine in THIS refactor. The Task 1.7
     forwarding adapter impls already let Engine call ports on its concrete fields.
